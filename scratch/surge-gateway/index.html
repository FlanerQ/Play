Mac mini Surge 网关方案

目标：快、低延迟、高安全。Mac mini 运行 Surge，作为我这一侧所有设备的代理网关。约束：OpenWrt 主路由同时接着我和室友两边，两边要各自独立、互不影响；主路由准备换新。服务端已部署 Xray VLESS + REALITY。

01

先说约束：Surge 能用哪些协议

Surge 官方手册的 Proxy Protocols 一节列出：HTTP/HTTPS/HTTP2、SOCKS5、Shadowsocks、Snell、VMess、Trojan、TUIC、Hysteria 2、MASQUE、AnyTLS、Trust Tunnel、SSH、WireGuard、Tailscale，以及 External Proxy Program。另外有 Shadow TLS（v2/v3）可以套在大部分 TCP 协议外面。

没有 VLESS，也就没有 XTLS Vision 和 REALITY。TLS 参数里也没有 uTLS 指纹伪装和 REALITY 选项。所以你现在的服务端，Surge 不能直接连。

好消息：你用的是 Mac 版。Surge Mac 支持 External Proxy Program：Surge 启动一个外部程序（sing-box），程序在本机开 SOCKS5 端口，Surge 把流量转给它。这样 REALITY 线路可以保留，只是多一个本地进程。iOS 版不支持这个功能。

03

各协议的优劣

Hysteria 2

主力
QUIC · TLS 1.3 · TCP 与 UDP 都能转发
  • 一条 QUIC 连接里多路复用，新请求不用再握手，延迟最低
  • 自带激进的拥塞控制（Brutal），丢包多的跨境线路照样能跑满带宽
  • Surge 支持端口跳跃，单个端口被限速时影响小
  • Mac 6.4.3+ 有 Salamander 混淆，iOS 5.20 / Mac 6.7+ 有 Gecko 混淆
  • 走 UDP，部分运营商高峰期会限速或丢弃 UDP，所以必须有 TCP 备用
  • 流量特征是 QUIC，隐蔽性不如 REALITY
  • 需要域名和证书（也可以自签名，再在 Surge 里固定证书指纹）

AnyTLS

TCP 备用
TLS · 流量填充 · 默认复用连接
  • 专门针对 TLS-in-TLS 特征设计，用灵活的填充打散流量形态
  • 默认开启连接复用，第一次握手之后，新请求几乎没有额外延迟
  • sing-box 原生支持入站，可以和 Hysteria 2 放在同一个进程里
  • UDP 通过 UDP over TCP 转发，不用额外配置
  • 需要你自己的域名和证书，域名一旦被标记就会被封
  • 比较新，需要 iOS 5.17 / Mac 6.4.3 以上
  • TCP 线路丢包时，吞吐不如 Hysteria 2

VLESS + REALITY + Vision

外挂兜底
你已部署 · 借用真实网站的 TLS 握手
  • 目前抗主动探测最强：探测者看到的是被借用网站的真实证书
  • 不需要自己的域名和证书
  • Vision 去掉了 TLS 套 TLS 的重复加密，转发效率高
  • Surge 不原生支持，只能在 Mac 上经 sing-box 外挂，多一层本地转发
  • Vision 不能和多路复用一起用，每个新连接都要 TCP + TLS 两个往返
  • iPhone 上的 Surge 用不了

Snell v5

可选
Surge 团队自研 · v5 支持 QUIC 代理模式
  • 为 Surge 设计，集成度最高，配置最简单
  • v4 起支持连接复用；v5 遇到 QUIC 流量会自动用 QUIC 代理模式转发，比逐个转发 UDP 包更高效
  • 可以套 ShadowTLS v3，借别人网站的握手来伪装
  • 不套 ShadowTLS 时，整条流量是看起来随机的加密数据，这正是“全加密流量”检测针对的特征
  • 协议和服务端闭源，没有公开规范和第三方审计
  • v6 加了流量整形，但还是 beta，官方说可能有不兼容的变更，而且 v6 去掉了 QUIC 代理模式

TUIC v5

可替代 HY2
QUIC · 用 UUID 加密码认证
  • 和 Hysteria 2 一样多路复用、低延迟，也支持端口跳跃
  • 拥塞控制可以选 BBR，对线路更温和
  • 同样受 UDP 限速影响，不能套 ShadowTLS
  • 在丢包严重的线路上，抢带宽的能力一般不如 Hysteria 2
  • Surge 区分 tuic（v4）和 tuic-v5，要和服务端版本对上

其他：Trojan / WireGuard / VMess

不推荐
能用，但这个场景下有更好的选择
  • Trojan：AnyTLS 可以看作它的改进版（有填充、默认复用），没理由再选 Trojan
  • WireGuard：加密很强、很快，但握手特征明显，在有审查的网络里很容易被识别
  • VMess：老协议，依赖时间同步，性能和隐蔽性都已落后

06

网络拓扑：现在和目标

主路由上要做的三件事

  1. 建两个接口和防火墙区。一个 me（192.168.10.0/24，包含 Mac mini 的网口和我的 Wi-Fi），一个 roommate（192.168.20.0/24，只包含接室友路由器的那个网口）。两个区都只允许转发到 wan，彼此之间不建转发规则。
  2. 室友区只给最少权限。roommate 区的入站默认拒绝，只放行 DHCP 和 DNS，这样他那边也登录不了主路由后台。
  3. 只有 me 区的 DHCP 下发 Mac mini。OpenWrt 可以按接口设置 DHCP 选项，选项 3（网关）和 6（DNS）填 192.168.10.2。室友区的 DHCP 保持默认。
OpenWrt UCI 示意（接口名、网口名按实际修改）
# me 区：网关和 DNS 指向 Mac mini
uci add_list dhcp.me.dhcp_option='3,192.168.10.2'
uci add_list dhcp.me.dhcp_option='6,192.168.10.2'

# 两个区：只允许各自出网，不建 me ↔ roommate 转发
uci add firewall forwarding; uci set firewall.@forwarding[-1].src='me';       uci set firewall.@forwarding[-1].dest='wan'
uci add firewall forwarding; uci set firewall.@forwarding[-1].src='roommate'; uci set firewall.@forwarding[-1].dest='wan'
uci set firewall.roommate.input='REJECT'   # 另加规则放行 udp 67-68（DHCP）和 53（DNS）

uci commit && service dnsmasq restart && service firewall restart
别让 Mac mini 自己拿到这个 DHCP 选项。Mac mini 如果也从 DHCP 拿地址，就会把网关指向自己，形成环路。Mac mini 必须手动设静态 IP，网关填主路由 192.168.10.1，DNS 填主路由或公共 DNS。

需要新的 AP 吗？

和上一版不同，现在答案取决于你选哪种新路由器：

  • 选一体机（路由和 Wi-Fi 在同一台）：不需要另买 AP，我的 Wi-Fi 由新主路由提供。
  • 选分体（推荐，见第 11 节）：路由盒没有 Wi-Fi，需要一台 AP 接在 me 区的网口上。你说想要“信号更稳”，这台 AP 正是解决这个问题的。
  • 室友那边：不用动，他继续用自己的路由器。

落地步骤

  1. 换主路由，先分好区。新主路由刷 OpenWrt 25.12，建 me 和 roommate 两个区（第 06 节）。室友路由器接到 roommate 口，确认他能正常上网，而且从他那边访问不到 192.168.10.x。
  2. 服务端加 sing-box。申请证书，按第 07 节起 Hysteria 2 和 AnyTLS，加端口跳跃规则，云厂商安全组放行 443/udp、20000–30000/udp、8443/tcp。
  3. Mac mini 准备。用网线接 me 区网口，手动设静态 IP 192.168.10.2，网关 192.168.10.1。系统设置里打开“显示器关闭时防止自动进入睡眠”和“断电后自动启动”，关掉自动安装更新后重启。
  4. Surge 单机验证。先不开网关，在 Mac mini 本机测通三条线路，看延迟和速度，确认 fallback 能切换。
  5. 开网关模式，用一台设备测试（方案 A）。手机手动把网关和 DNS 设成 192.168.10.2，确认能上网、规则生效、Surge 设备列表里能看到这台手机。
  6. 处理 IPv6。在主路由的 me 接口上关掉 IPv6（RA/DHCPv6），否则我的设备会走 IPv6 绕过 Mac mini，见第 10 节。室友区可以保留 IPv6。
  7. me 区全部生效（方案 B）。给 me 区的 DHCP 加上选项 3 和 6。留一台设备设成静态 IP、网关指向 192.168.10.1，作为应急入口。
10

风险与坑

单点故障 高

Mac mini 关机、睡眠或 Surge 崩溃，我这一侧断网（室友不受影响）。对策：禁止睡眠；保留路由器 DHCP 一键恢复的办法；准备一台静态 IP 的应急设备。

IPv6 绕过 高

主路由还在给 me 区发 IPv6 地址的话，设备会直接走 IPv6 出网，不经过 Mac mini。最简单的做法是关掉 me 接口上的 IPv6。

UDP 被限速 中

部分运营商会对 UDP 限速或干扰，Hysteria 2 速度会突然掉。fallback 组会切到 AnyTLS；Hysteria 2 也可以考虑开 Salamander 或 Gecko 混淆。

UDP Fast Path 中

Surge Mac 6.4.0+ 的网关模式里，短时间内连接数很多的设备（典型如游戏、P2P）会被切到三层直接转发，这部分流量不经过代理，规则也不生效。可以在 Dashboard 或设备列表里给单个设备固定行为。

设备自带加密 DNS 中

Chrome 安全 DNS、Android 私人 DNS、iCloud 专用代理会绕开 Surge 的 DNS。Surge 仍然能按 IP 和 SNI 分流，但基于域名的规则可能不准。需要时在这些设备上关掉这些功能。

Wi-Fi 当网关 中

Mac mini 如果走 Wi-Fi，所有流量要在无线上来回两次，延迟和吞吐都会变差。一定要用网线。

Snell v6 beta 低

想试 Snell 的话先用 v5。v6 官方标注为 beta，协议可能不兼容地变更。

Mac mini 拿到指向自己的网关 高

me 区的 DHCP 选项会让所有 DHCP 客户端把网关设成 .2，Mac mini 自己也不例外。Mac mini 一定要手动设静态 IP，网关填主路由。

分区没隔干净 中

换完路由后从室友那边 ping 一下 192.168.10.1 和 Mac mini，应该都不通（DHCP、DNS 除外）。也检查一下 Wi-Fi 是否只桥接在 me 接口上。

网关只对局域网开放 默认安全

gateway-restricted-to-lan 默认开启，只接受本网段设备，就算误配了 DMZ 也不会暴露到公网。保持默认。

换什么路由器

代理已经交给 Mac mini 上的 Surge，所以主路由不需要跑代理插件，也就不需要多强的 CPU。它要做好的是三件事：分区隔离（VLAN 和防火墙）、稳定的 Wi-Fi、足够多的有线口。我这侧至少要接 Mac mini 和 AP，加上 WAN 和室友，一共 4 个口。

路线型号芯片 / 接口Wi-Fi主线 OpenWrt适合谁
分体推荐路由盒：x86 四网口小主机（N100/N150 级别，4×2.5G）或 Banana Pi BPI-R4
Wi-Fi：一台 Wi-Fi 7、2.5G 上联的 AP，用原厂固件跑 AP 模式		x86：4×2.5G
BPI-R4：MT7988A，带 10G SFP		由 AP 负责路由盒有官方镜像要信号稳、要性能、以后想单独升级 Wi-Fi
一体机·稳妥GL.iNet Flint 2（GL-MT6000）MT7986 四核 2.0 GHzWi-Fi 6 双频 4×4，没有 6 GHz官方镜像不想折腾，一台搞定，约 170 美元
一体机·Wi-Fi 7GL.iNet Flint 3（GL-BE9300）IPQ5332，5×2.5GWi-Fi 7 三频未支持，开发中要 Wi-Fi 7，接受用 GL 官方固件（基于 OpenWrt 23.05 定制）
商业生态UniFi 网关 + U7 系列 AP—Wi-Fi 7不是 OpenWrt想要 App 管理、开箱即用，接受定制能力弱

为什么推荐分体

  • Wi-Fi 交给原厂驱动最稳。Wi-Fi 7 在主线 OpenWrt 里还不成熟：Flint 3 的高通 Wi-Fi 驱动还在开发中，联发科的 Wi-Fi 7 设备也还在陆续合入
  • 路由用 OpenWrt 最灵活。分区、防火墙、按接口下发 DHCP 选项，都是 OpenWrt 的强项
  • 可以分开升级。Wi-Fi 8 出来只换 AP，路由盒不动
  • 网口够用。x86 小主机一般有 4 个 2.5G 口，WAN、Mac mini、AP、室友正好

选购时要核对的

  • 到 OpenWrt 官方硬件表（Table of Hardware）确认型号和硬件版本都在支持列表里
  • AP 必须支持 VLAN 或纯 AP 模式，上联口最好是 2.5G
  • BPI-R4 是开发板，要自己配外壳、电源和 Wi-Fi 模块，不适合想省事的人
  • 价格和型号来自 2026 年的公开评测，购买前以官方页面为准

AI 时代，OpenWrt 还是最好的选择吗

做路由，是。理由反而因为 AI 变得更充分了：

系统配置方式AI agent 能否操作Wi-Fi代理生态评价
OpenWrt 25.12文本配置（UCI）+ SSH + LuCI 网页最好 读写配置文件、跑命令都行Wi-Fi 7 不成熟sing-box、homeproxy、OpenClash路由的首选
ImmortalWrt同 OpenWrt好同 OpenWrt内置包更多国内常用的 OpenWrt 分支，软件源更方便
OPNsense / pfSense网页 + API + SSH好基本不做 Wi-Fi一般x86 防火墙很强，但要另配 AP
UniFiApp / 网页，有 API一般 以图形界面为主体验好弱省心，但能改的东西少
原厂固件网页 / App差 只能点界面驱动最稳基本没有适合当纯 AP

“AI native” 真正意味着什么

  • 原厂路由器宣传的“AI 加速”“AI 漫游”“AI 安全”，大多是营销名词下的 QoS 和信号调度，不构成换系统的理由
  • 真正有用的是能让 AI agent 接手运维：配置是纯文本、能 SSH、能写脚本、改动能放进 git 管理。OpenWrt 全部满足
  • 和第一轮聊的内容连起来：在 Mac mini 上用 Remote Control 跑 Claude Code，它就在你的局域网里，可以直接 SSH 到 OpenWrt 帮你改配置、排查问题

版本提醒

  • 当前稳定版是 25.12 系列（2026 年 3 月发布，维基百科记录最新为 25.12.5），包管理器从 opkg 换成了 apk，命令写法不同
  • 官方说明 24.10 在 2026 年 9 月之后不再提供安全更新。你现在的主路由如果还是 24.10，已经停止安全更新了，这也是换机的一个理由
